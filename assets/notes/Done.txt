Fixed:
- fix(rescue): kill the main app process automatically every time the Rescue Center opens
  - Root cause: rescue write actions (e.g. the database export) refuse to run while the main process is alive, so the user had to go to Android Settings > Force stop before any rescue write could succeed
  - New `RescueProcess` object in `core/rescue`: `requestKillMain(context)` sends an intra-app broadcast (`ACTION_KILL_MAIN`, always `setPackage` to the app's own package) AND writes a safety-net flag file (`rescue_kill_main.flag` in filesDir) — fire-and-forget: a failed broadcast is only logged, the flag still covers the request, and vice versa
  - `MainApplication.kt` `onCreate`: right after the `isMainProcess()` guard and BEFORE any heavy init, `consumeKillRequest` is checked — if a kill request is pending the process ends itself (`Process.killProcess(myPid)`, the public API; the framework's `exitProcess` is @hide); `registerKillMainReceiver()` is then registered early (before `Dependencies.init`) on the main process only
  - The kill receiver runs on `RescueProcess.KILL_REQUEST_HANDLER`, a dedicated daemon `HandlerThread` ("nzik-rescue-kill"): a manifest receiver or a handler-less one would be invoked on the main thread — precisely the thread frozen during an ANR — so the background looper can receive the broadcast while the main thread is stuck; `RECEIVER_NOT_EXPORTED` from API 33 (setPackage-only below) keeps the broadcast invisible outside the app
  - `RescueActivity.kt`: `onCreate` calls `RescueProcess.requestKillMain(this)`, so both entry points (launcher shortcut and in-app burger menu) trigger the kill
  - `RescueScreen.kt`: while a request is pending, a status poll (`LaunchedEffect(killRequestGeneration)`, 1 s cadence on `RescueFiles.isMainProcessRunning`) reports "stopping" then "stopped" and calls `cancelKillRequest` as soon as the death is observed (a stale request must never self-kill the next healthy launch); manual "Kill the app" `RescueActionCard` added in the Danger Zone to re-send the request after a failed kill; `guardWrite` untouched
  - `strings.xml`: 2 adjusted keys (`rescue_main_process_running`, `rescue_error_database_busy`) + 5 new keys (`rescue_status_main_process_stopping`, `rescue_status_main_process_stopped`, `rescue_kill_app`, `rescue_kill_app_description`, `rescue_confirm_kill_app`)
  - New `RescueProcessTest.kt` (9 JUnit5 tests: flag write/consume/idempotence/overwrite/cancel/parking-file) and `RescueProcessRequestTest.kt` (2 Robolectric tests: the broadcast reaches the intra-app receiver with the right action/package, and a failed kill can be re-sent) — 58/58 package tests pass
  - Deviations: `Process.exitProcess` is @hide → `Process.killProcess(myPid)`; public Android has no executor-based `registerReceiver` → the receiver is bound to a `HandlerThread`
