Fixed:
- fix(discordrpc): stop re-sending album art on every refresh tick — reuse the resolved asset when the song is unchanged (spec `spec-discord-rpc-reuse-artwork-same-song`)
  - Root cause: `DiscordRpcConnection.setActivity` sent the presence in two phases on every call — phase 1 without the assets, phase 2 with them — so the app's 5 s refresh tick stripped and re-added the artwork every tick (constant flash + a transient image-less fallback whenever phase 2 was slow, superseded or failed)
  - New private `lastLargeAsset`/`lastSmallAsset` fields in `DiscordRpcConnection` remember the assets actually resolved and sent, paired with `lastLargeImage`/`lastSmallImage`; on a same-image tick phase 1 now carries the reusable assets and phase 2 is skipped entirely — one complete send per tick, no re-upload, no flash
  - Two-phase flow kept for genuinely new images; failed uploads are never remembered (stay null) so the next tick retries via the normal two-phase path; the remembered assets are invalidated when the raw image changes and reset by `clearArtworkCache()` (a new account never reuses the previous account's uploads)
  - Review patch (gate 8b, bmad-code-review 4 layers): an `assetLock` synchronizes the (image, asset) pairing across threads — the phase-2 write-back (background dispatcher) re-checks the activity id under the lock before remembering, so an interleaving song skip can never leave the previous song's asset paired with the new image (stale artwork sent forever, phase 2 skipped)
  - Tests: `DiscordRpcConnectionTwoPhaseTest` 12 → 15 (`a repeated same-image setActivity reuses the uploaded asset and sends once`, `after a failed upload the next same-image tick retries and later ticks reuse the asset`, plus review patches `a remembered asset is never sent for a different image, even if the new upload fails`, `a stable large+small tick reuses both assets and a song switch keeps the small asset`, `clearArtworkCache resets the remembered assets so the next tick re-uploads`); module suite 58/58, `:ComposeN-Zik:assembleDebug` OK
  - Verified on device with a signed dev build (2026-10-09): same song → the artwork is kept across refresh ticks, no flash, no re-upload; a new song takes the two-phase path once
