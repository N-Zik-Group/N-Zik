fix(shortcuts): launcher shortcut icons stuck white on Pixel despite theme-adaptive design (_bmad-output/implementation-artifacts/spec-shortcuts-theme-icons-build-links.md)
  - Started as a bug report mid-review of a separate shortcuts feature (theme-adaptive icons + per-build-type links, built in a different session): on Pixel, shortcut icons showed white instead of the required "always black" — the "Option A" fix that session had written (push a same-id dynamic shortcut with a fixed black bitmap icon on the Google launcher) was marked "to verify on-device" and never actually tested
  - **Root-caused with real on-device/emulator verification (adb/dumpsys/logcat) at every step, not assumption:** (1) `homeLauncherPackage()` always returned `null` — Android 11+ package visibility requires a `<queries>` manifest entry to resolve another package's `ACTION_MAIN`/`CATEGORY_HOME` activity, which was missing; added it, confirmed the launcher (`com.google.android.apps.nexuslauncher`) now resolves. (2) Once resolved, "Option A" itself turned out to be platform-impossible: `ShortcutManager.setDynamicShortcuts`/`disableShortcuts` both threw `IllegalArgumentException: Manifest shortcut ID=... may not be manipulated via APIs` — a manifest (static XML) shortcut is fully immutable at the OS level, no mutation (add/update/disable) is permitted via the API once its id exists in the manifest, ruling out both "override by same id" and "disable static + add dynamic under a different id"
  - **Fix (user-approved redesign, "tout dynamique"):** removed the 5 static `shortcuts.xml` files (androidMain/debug/foss/dev/dev32) and the manifest's `android.app.shortcuts` meta-data entirely. `shortcuts/ShortcutIconSync.kt` renamed to `registerAppShortcuts(context)`, called from `MainActivity.onCreate`: registers all 4 shortcuts purely as dynamic shortcuts on every launch, with `Icon.createWithResource` (theme-adaptive, resolved by the launcher exactly like a manifest icon would be) on any launcher, or `Icon.createWithBitmap` (fixed black, via a new `tintedBitmap` helper) on the Google/Pixel launcher. Bonus: `Intent(context, MainActivity::class.java)` resolves the right package regardless of `applicationIdSuffix`, making the per-build-type `shortcuts.xml` overrides unnecessary too
  - Trade-off accepted by the user: shortcuts no longer exist until the app has been launched at least once after install (previously available immediately via the manifest, on every launcher, not just Pixel)
  - Verified on a Pixel_10_Pro_XL emulator: `dumpsys shortcut` shows all 4 shortcuts flagged dynamic with a real saved bitmap (`bitmapPath=...png`, no `iconRes`), matching log `"Google launcher: registered shortcuts with fixed black icons"`; black icons confirmed visually by the user on the emulator
  - `ShortcutResourcesTest.kt` (tested the now-deleted static `shortcuts.xml`) removed; `ShortcutIconSyncTest.kt` rewritten: launcher detection (unchanged), `shortcutSpec` id→resource/action mapping (plain JVM), `shortcutIcon`/`tintedBitmap` icon-type and size (Robolectric) — exact tint-color fidelity isn't verifiable in Robolectric here (its `ColorDrawable`/`ShapeDrawable` shadow doesn't apply `DrawableCompat.setTint` during `draw()`, confirmed by a failing assertion), so that's left to the real on-device verification above rather than asserted in the unit test
  - Briefly tried enabling `testOptions.unitTests.isIncludeAndroidResources` to load real resources in tests instead — reverted immediately, it regressed ~36 unrelated tests via a JVM security-provider conflict (`KeyStoreException`/`NoSuchAlgorithmException`)
  - **Follow-up, same session: shortcuts tapped while the app was already running (any of the 5 actions) did nothing — only a cold start worked.** Root-caused and fixed in 3 steps, each verified on-device (adb `am start -a <action>` while the app stayed open, screenshotted):
    1. `MainActivity.onNewIntent` updated `intentUriData` (deep links) but never called `setIntent(intent)` nor touched anything Compose-observable for the shortcut action — the composable kept reading the stale launch-time `intent.action` forever. Added a `private var shortcutIntentAction by mutableStateOf<String?>(null)` (same pattern as `intentUriData`), set from both `onCreate` and `onNewIntent` (which now also calls `setIntent(intent)`)
    2. First attempt regressed: resetting `shortcutIntentAction = null` synchronously inline in the composable (mirroring the old raw-`Intent.action = null` mutation) raced with `HomeScreen`'s `LaunchedEffect(openTabFromShortcut)` — both the -1→X and the immediate X→-1 recomposition could settle before that effect ever ran, silently dropping the navigation. Fixed by resetting from a `LaunchedEffect(shortcutIntentAction)` instead (matching how `intentUriData` already resets itself at the end of its own effect, a few lines below)
    3. Two more gaps found only by testing every one of the 5 shortcuts repeatedly, not just search once: (a) `HomeScreen`'s tab-shortcut handling (songs/albums/artists/library) only ever read `openTabFromShortcut` through a `remember`ed snapshot taken at first composition — live taps while the app stayed open never switched tabs (search alone had a dedicated live `LaunchedEffect`). Added an equivalent `LaunchedEffect(openTabFromShortcut)` for tabs, plus `shouldSwitchTabFromShortcut`/`tabIdForIndex` helpers. (b) `searchShortcutConsumed` (a `rememberSaveable` one-shot gate) latched permanently for the composable's whole lifetime instead of per-occurrence — search worked exactly once per app process, never again. Fixed by resetting that flag back to `false` as soon as the sentinel moves off `OPEN_SEARCH_SHORTCUT`, so each new live occurrence is treated as fresh while still guarding against the same occurrence re-firing across an unrelated recomposition. (c) None of the above helped if a *different* screen (e.g. search) was already on top of the back stack when a tab shortcut was tapped — `HomeScreen` isn't part of the composition while another destination is active, so its effects never ran regardless. Fixed with a `currentBackStackEntryAsState()`-driven effect in `MainActivity` that pops back to `NavRoutes.home.name` first and only clears `shortcutIntentAction` once the back stack has actually settled on home, giving `HomeScreen` a real chance to observe the value once it reappears
  - New test: `shouldSwitchTabFromShortcut` case added to `ResolveInitialTabIndexTest.kt`

Fixed by replacing `makeRateLimitedRequest` (wrapped a whole logical operation) with `rateLimitedGet(url)` (wraps every individual HTTP call) and rewriting `fetchArtistMetadata`/`fetchAlbumMetadata`/`fetchArtistRelations` to call it per-request
  - `MusicBrainz.kt`: added a circuit breaker — after 3 consecutive failures the client refuses all further requests for 10 minutes (`circuitOpenUntil`, checked in `rateLimitedGet` before even attempting a request). Applies uniformly to auto on-view sync, manual force-resync, and `MbBackfillWorker` since they all share the one `MBMetadataHelper.Default`/`MusicBrainz` instance — a spammed resync button or a broken worker can no longer keep hammering MusicBrainz once it's clearly down. Exposed via `circuitOpenRemainingMs()`/`MBMetadataHelper.circuitOpenRemainingSeconds()`
  - `InfoAndCommunity.kt`/`AlbumScreen.kt`/`ArtistScreen.kt`: resync now surfaces the circuit-breaker state distinctly instead of the generic failure message — toast "MusicBrainz paused after repeated failures — retry in Xmin" and status line "Paused (too many failures): retry in Xmin" (red, highest priority over Never synced/Sync failed) when the breaker is open, both on auto-sync and manual resync
  - `MusicBrainz.kt`: fixed the User-Agent — per https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting MusicBrainz requires `Application/version ( contact-url )` with a real contact point, not a bare package id; was `n-zik/$appVersion ( com.nevar.nzik )`, now `N-Zik/$appVersion ( https://github.com/N-Zik-Group/N-Zik )`
  - `MbBackfillWorker.kt`: added +/-15min jitter to both the initial 1h delay and the 24h reschedule, per MusicBrainz's explicit guidance to avoid synchronized requests across distributed installations (every install of a new version hitting MB at the same fixed offset)
  - `AlbumInsightsViewModel.kt`: removed the background bulk-backfill loop that MusicBrainz-fetched every "Other albums"/"Singles & EPs" candidate (commonly 10+) just from opening one album's Insights page — that fan-out from a single page view is exactly the bulk-fetch pattern MusicBrainz's rate limiting exists to discourage; MB metadata for those items is now only fetched when the user actually opens that specific album
  - `MusicBrainz.kt`: `fetchArtistMetadata`'s artist-name search query was never URL-encoded (unlike the release-group search, which already used `URLEncoder.encode`) — an artist name containing `&`, `+`, `#`, or similar (e.g. "Guns N' Roses", "Earth, Wind & Fire") would silently break the query and waste a rate-limited request on a lookup that could never match; fixed to encode it the same way
  - `MusicBrainz.kt`/`MainApplication.kt`: the circuit breaker's `circuitOpenUntil` and `consecutiveFailures` are now persisted to SharedPreferences (`mbCircuitOpenUntilKey`, `mbCircuitFailuresKey` in `Preferences.kt`) instead of living only in the in-memory `MusicBrainz` singleton — force-quitting the app during a MusicBrainz outage no longer silently resets the breaker and lets the app start hammering it again; both a fresh failure and a reset-to-zero on success go through the property's persisted setter, so the streak survives restarts either way.
